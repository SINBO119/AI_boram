# planner-comments — 기획자용 한국어 주석 달기

화면 코드에 기획자가 읽을 수 있는 한국어 주석을 단다.
주석은 "이 코드가 화면에서 무엇을 하고, 어떤 기획 근거(F-xx, Rx)를 따르는지"를 설명한다.
**코드 동작은 절대 바꾸지 않는다. 주석만 추가한다.**

## 1. 작업 순서

### 1-1. 대상 정하기
- 인자(`$ARGUMENTS`)로 받은 파일 또는 폴더를 대상으로 한다.
- 인자가 없으면 화면 코드 파일(예: `pages/`, `screens/`, `app/`, `components/` 아래의 화면 파일)을 찾아 목록을 보여 주고, 사용자 확인을 받은 뒤 진행한다.
- 대상 파일을 고치기 전에 원본을 스크래치 디렉터리에 백업한다(5장 확인과 되돌리기에 쓴다).

### 1-2. 근거 문서 읽기
아래 순서로 읽는다. 내용이 서로 다르면 앞의 문서를 따른다 (`reference/links.md`의 우선순위).

1. `docs/PRD.md` — 기능 ID(F-xx), 범위, 열린 질문(Q#)
2. `docs/screens.md` — 화면 목적, 들어오는 곳·나가는 곳
3. `docs/DOMAIN.md` — 용어집, 비즈니스 규칙(R1~R12)

### 1-3. 코드와 근거 연결하기
- 각 화면 파일을 PRD 6장의 화면(추천 / 목록 / 상세)과 screens.md의 화면에 연결한다.
- 화면 안의 영역·컴포넌트·조건문·계산을 기능 ID(F-xx)와 규칙 ID(Rx)에 연결한다.

### 1-4. 주석 달기
다음 세 곳에 단다.

| 위치 | 내용 |
|---|---|
| 파일 맨 위 | 화면 이름, 목적, 들어오는 곳·나가는 곳, 관련 기능 ID |
| 주요 영역·컴포넌트 | 이 영역이 화면에서 보여 주는 것, 관련 ID |
| 분기·계산·조건문 | 어떤 조건에서 무엇이 달라지는지, 판단 기준, 관련 규칙 ID |

### 1-5. 문서에 없는 동작 처리
- 문서에 정해지지 않은 동작이고 관련 열린 질문이 있으면: `미정 (Q#)`으로 표시한다.
- 관련 열린 질문도 없으면: `확인 필요`로 표시하고, 보고서의 "확인 필요" 목록에 넣는다.

### 1-6. 보고서 만들기
`docs/comments-report.md`를 만든다(있으면 갱신한다). 형식은 3장을 따른다.

## 2. 주석 형식

- 모든 주석 앞에 `[기획]`을 붙인다. 개발자 주석과 구분하고 검색하기 위해서다.
- 파일 맨 위는 블록 주석 `/** */`, 나머지는 한 줄 주석 `//`을 쓴다. JSX 안에서는 `{/* */}`를 쓴다.
- 문체는 "~한다" 체로 쓴다.
- 한 주석은 최대 3줄이다. 더 길어지면 ID만 적고 PRD를 참고하도록 한다.
- 근거가 있으면 끝에 ID를 괄호로 적는다. 예: `(F-A6, R6)`

**예시**

```tsx
/**
 * [기획] 요금제 추천 화면
 * 고객의 최근 3개월 사용량을 근거로 요금제 2~3개를 추천한다. (F-A1~F-A9)
 * 들어오는 곳: 서비스 시작 / 나가는 곳: 요금제 상세
 */

// [기획] 지금 완전 무제한을 쓰면 혜택 기준 추천(B)으로 보낸다. (R9)
if (currentPlan.dataType === 'UNLIMITED') { ... }

// [기획] 한 단계 아래 요금제는 기본 제공량이 평균 사용량 이상일 때만 보여 준다.
// [기획] 이때 "가장 많이 쓴 달에는 모자랄 수 있음"을 함께 표시한다. (F-A6, R6)
if (lowerPlan.baseData >= avgUsage) { ... }

{/* [기획] 대안에도 +20% 요금 상한을 적용할지는 미정 (Q4) */}
```

## 3. 보고서 형식 (`docs/comments-report.md`)

```markdown
# 기획 주석 보고서

## 작업한 파일
| 파일 | 화면 | 주석 수 |

## 화면별 기능 ID 연결
| 화면 | 연결한 ID | 연결하지 못한 ID (해당 화면의 PRD 기능 중) |

## 미정
| 파일:줄 | 내용 | 열린 질문 |

## 확인 필요
| 파일:줄 | 내용 | 기획자에게 물을 것 |
```

## 4. 꼭 지킬 것

1. **코드 동작을 바꾸지 않는다.** 주석 외의 코드는 공백 하나도 바꾸지 않는다. 기존 주석은 고치거나 지우지 않는다.
2. **쉬운 말로 쓴다.** 개발 용어는 풀어 쓴다.

   | 쓰지 않음 | 이렇게 씀 |
   |---|---|
   | state | 화면이 기억하는 값 |
   | props | 화면에 넘겨받는 값 |
   | API 호출 / fetch | 서버에서 데이터를 불러온다 |
   | render | 화면에 보여 준다 |
   | 조건부 렌더링 | ~일 때만 보여 준다 |

   변수명이나 함수명을 꼭 적어야 하면 괄호 안에 한 번만 쓴다.
3. **DOMAIN.md 용어집의 표현을 쓴다.** "요금"이라고 뭉뚱그려 쓰지 않고 "월정액"과 "할인 후 실납부액"을 구분한다. "데이터량"이라고 쓰지 않고 "사용량"과 "기본 제공량"을 구분한다.
4. **추측하지 않는다.** 문서와 코드 어디에도 근거가 없는 의도는 지어내지 않고 `확인 필요`로 남긴다.
5. **개인정보를 쓰지 않는다.** 주석과 보고서에 고객의 이름, 연락처 같은 개인정보를 쓰지 않는다. 예시에는 가상의 수치만 쓴다.
6. **주석을 달지 않는 곳**: import, 스타일 값, 뜻이 뻔한 한 줄 코드. 화면에 보이는 동작이나 판단 기준이 있는 곳에만 단다.

## 5. 끝났는지 확인

모두 통과해야 완료다. 하나라도 통과하지 못하면 고친 뒤 다시 확인한다.

1. **동작 확인**
   - 백업한 원본과 `diff`로 비교해, 추가된 줄이 모두 `[기획]` 주석이고 삭제·변경된 줄이 없는지 확인한다.
   - 프로젝트에 빌드·타입 검사·린트 명령이 있으면 실행해 통과하는지 확인한다.
2. **빠진 곳 점검**
   - 대상 화면 파일마다 맨 위에 `[기획]` 블록 주석이 있다.
   - 해당 화면의 PRD 기능 ID가 모두 연결됐다. 연결하지 못한 ID는 보고서에 적었다.
3. **규칙 점검**
   - 모든 추가 주석이 `[기획]`으로 시작하고, "~한다" 체이며, 3줄 이하다.
   - 4장 2번의 금지 용어가 남아 있지 않다.
   - 개인정보가 없다.
4. **검토 받기**
   - 사용자에게 바뀐 파일과 주석 예시 몇 개를 보여 주고 승인을 받는다.
   - 사용자가 거절하면 백업으로 되돌린다.
5. **완료 보고**
   - 채팅에 짧게 알린다: 작업한 파일 수, 추가한 주석 수, "미정"·"확인 필요" 건수, 보고서 링크(`docs/comments-report.md`).
